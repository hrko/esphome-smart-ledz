# 実機による通信タイミングの調査 — 2026-10-12

## 調査対象と構成

USB接続したESP32-S3から、既存の検証用設定に登録されている照明1台（メッシュアドレス`0x0001`）を操作した。対象器具はユーザーが指定し、点灯状態の目視確認にも協力いただいた。以下の結果は、この器具とBLE接続環境で得られたものであり、他の器具やグループ制御での動作は未確認である。

- ハブの基準コミット：`74c437e34da2c4db57f84e0381c84d866aa52d5c`
- 通信ライブラリ：`bf289fc21f58f15e9c40e2ed82639a99d2185aff`
- プロトコルライブラリ：`f70f4a028ce70769bd670deecdb663f549905550`
- ESPHome 2026.9.1、ESP-IDF 5.5.5、ESP32-S3リビジョン0.2
- 応答ありのGATT書き込み、既存の再試行・キュー処理、2秒間隔のポーリングを使用
- 試験前の状態：ON、明るさ71%、RGB `(194,111,5)`

製品コードと既定値は変更していない。Git管理対象外のコンポーネントのコピーに、送信・GATT書き込み完了・復号後の状態応答の時刻を記録する処理と、対象をアドレス1に限定したUSBコマンド受付処理を追加した。操作には既存のハブの公開メソッドを使い、仕様不明のopcodeは送信していない。

計測用ファームウェアのビルドと書き込みは成功した。シリアルログの出力がタイミングに影響する可能性があるため、測定値には計測処理の影響が含まれる。また、USBコマンドはESPHomeの照明状態処理を経由しない。この試験で確認した範囲はプロトコルとハブの動作であり、Home Assistant連携を含む完成した実装の検証は行っていない。

## 消灯中の色設定

次の順序で操作した。コマンドとペイロードの表記は16進数である。

1. `D0 [00]`で消灯する。
2. `E2 [04,50,6E,B4]`でRGB `(80,110,180)`を設定する。
3. 状態を問い合わせた後、`D0 [01]`で点灯する。

消灯中の`DB`応答には新しいRGB値が含まれ、ペイロードのバイト6（先頭を0とする）は0のままだった。色設定後も消灯を維持していることをユーザーが目視で確認した。ON後も`DB`応答のRGB値は維持され、バイト6は`0x47`（71）に変わった。ユーザーは、以前の暖色を経由せず、最初から青寄りの色で点灯したと確認した。

この結果から、対象器具では消灯中にRGBを設定・保持できると分かった。2CH器具の`E2 [05,ct]`については未検証である。このコンポーネントのSYNCA色温度制御はRGB変換を使うため、同じ順序を適用できる可能性があるが、複数の色温度設定での検証は行っていない。

## 明るさ設定による点灯

別の試験として、消灯後にONコマンドを送らず、`D2 [23]`で明るさ35%を設定した。器具からは明るさ`0x23`を含む`DC`通知が返り、`DB`応答のバイト6も`0x23`になった。ユーザーも点灯を目視で確認した。

したがって、この器具では明るさ設定を「消灯を維持した事前設定」として扱えない。一方、希望する明るさで点灯させる最後の操作として利用できる。

状態確認では、消灯中も`F0`による調光値の読み出しが保存済みの明るさ（71%または35%）を返した点に注意が必要である。同じ消灯状態で、`DC`通知の明るさと`DB`応答のバイト6は0だった。調光値が0以外であることだけでは、点灯中と判断できない。また、最初のポーリングではON/OFF状態を取得できず、ON/OFF操作後に`DC`通知が届いた。このため、復元用の状態を保存する前に、最初の点灯状態を目視で確認した。

## 色設定と明るさ設定による2コマンドの点灯

消灯中にRGB `(40,120,80)`、明るさ45%の順でキューへ登録した。ONコマンドは送らず、送信間隔の既定値120msと応答あり書き込みを維持した。

| 記録した事象（起動からの経過時間、ms） | 1回目 | 2回目 |
| --- | ---: | ---: |
| USBからRGBコマンドを受け付け | 169117 | 253106 |
| RGBの書き込みを要求 | 169118 | 253107 |
| RGBの書き込み完了 | 169174 | 253155 |
| 明るさの書き込みを要求 | 169239 | 253235 |
| 明るさ45%を示すDC通知を受信 | 169303 | 253326 |
| RGBと出力45%を示すDB応答を受信 | 169601 | 253623 |

コマンド受付から`DC`通知までの時間は186msと220msだった。これは通知までの時間であり、光の変化を測定した値ではない。その後の`DB`・`F1`応答でも、指定した色と明るさを確認した。

ユーザーは1回目の点灯を見逃した。2回目は淡い緑色かどうかを判別できなかったものの、以前の暖色は見えなかったと回答した。したがって、2回とも指定した色を目視で完全に確認できたとは扱わない。

既存の照明出力処理では、ON、明るさ、色の順で送信する。ON後に400msの保留が入り、さらに明るさと色の間に送信間隔が入る。今回の2コマンド方式では、独立したONの書き込みと、それに伴う保留を省けた。既存方式についても、光の変化の時刻は測定していない。

## 送信間隔による明るさの追従性の比較

各設定で、明るさ35〜64%の30個の値を80ms間隔を目標に入力した。入力後は待機して最終状態を問い合わせ、試験前の状態へ戻した。既存のキュー処理は未送信の途中値を最新値へ統合する。各条件は短時間の試験1回であり、入力間隔も実測した。

| 測定項目 | 120ms設定 | 80ms設定 | 60ms設定 |
| --- | ---: | ---: | ---: |
| 受け付けた入力コマンド数 | 30 | 30 | 30 |
| 入力間隔の中央値 | 80ms | 84ms | 84ms |
| 明るさ変更中のD2送信数 | 20 | 28 | 28 |
| D2書き込みの成功数 | 20 | 28 | 28 |
| 明るさ変更中のDC通知数 | 20 | 28 | 28 |
| 実際のD2送信間隔の中央値 | 127ms | 85ms | 85ms |
| D2書き込み完了までの時間の中央値 | 62ms | 85ms | 85ms |
| D2書き込み完了までの時間の最大値 | 105ms | 127ms | 127ms |
| 最後の入力から64%を示すDC通知まで | 188ms | 119ms | 118ms |
| D2書き込みエラー数 | 0 | 0 | 0 |

すべての条件で最終値64%に到達した。これらの試験中にD2の再試行や切断は発生していない。入力数より送信数が少ないのはキューで途中値を統合したためであり、パケット欠落を測定した結果ではない。最初の予備試験はシリアル読み取りのタイムアウトが長く、複数の入力をまとめて送る状況が生じたため、比較表から除外した。

80ms設定では、途中の明るさを送信できた回数が増えた。60ms設定では、書き込み完了までの時間が次の送信を制限し、80ms設定からの実質的な改善は見られなかった。ただし、長期安定性、電波干渉下の挙動、複数器具への送信の公平性、RGB・色温度の連続変更については未検証である。応答なし書き込みも試していない。

## 実装への適用と残る検証

最初の改善候補は、対象機種を限定して選択できる点灯手順を追加することである。消灯中にRGBを設定し、その後に0以外の明るさを設定する。初期段階では、応答あり書き込み、再試行の上限、現在の送信間隔を維持する。

製品コードへ適用する際は、キューで値を統合しても同じ宛先への操作順序を保ち、OFFや切断で不要になった操作を取り消す必要がある。また、色設定に失敗した場合に後続の明るさ設定を送らないようにする。GATT書き込みの成功だけでは、メッシュ先の器具に色が反映されたことを保証できないため、状態確認とメッシュ内での通信欠落時の挙動も検証が必要である。

80msは追従性改善のための選択肢となるが、既定値を置き換えられるほどの検証は行っていない。点灯手順の変更と送信間隔の調整を分ければ、それぞれの効果と不具合を切り分けて評価できる。

残る検証対象は、他機種、2CHの色温度コマンド、グループ、一斉送信、短時間のOFF/ON切り替え、2コマンドの途中での切断・再試行、別の中継器具を経由する操作、長時間運転、光の変化の時刻測定である。

## 点灯方式の実装とコード検証

実装では、SYNCAの個別器具に対する既定の点灯方式を`color_then_brightness`とした。オンライン状態通知で消灯を確認できた場合に、RGBの書き込み応答を待ってから明るさを送る。色温度指定もRGBへ変換して同じ手順を使う。状態不明、グループ、一斉送信、接続先指定、他機種では従来手順を使い、個別の照明設定で`turn_on_mode: legacy`を指定すると常に従来手順へ戻せる。

送信間隔120ms、応答あり書き込み、各段階の最大3回の送信試行は維持した。色設定の失敗時には明るさへ進まない。待機中の設定変更では新しいRGB・明るさへ置き換え、OFFでは未送信の段階を取り消す。すでに送信したパケットは取り消せない。切断時には処理を破棄し、再接続時に再送しない。

これらの順序、取り消し、エラー処理、設定値の検証はホスト上の回帰テストで確認した。ESPHome 2026.9.1でESP32-S3向けのビルドも確認した。この実装変更後のファームウェアは、まだ検証用ESP32へ書き込んでいない。上記の実機試験結果と、今回のコードに対するテスト結果は区別する必要がある。
